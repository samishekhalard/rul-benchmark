# Прогнозирование остаточного ресурса оборудования: сравнение архитектур

*[English](README.md) · Русский*

Воспроизводимое сравнение нейросетевых и классических моделей для задачи
прогнозирования остаточного ресурса (Remaining Useful Life, RUL)
промышленного оборудования на датасете NASA C-MAPSS.

Репозиторий сопровождает две опубликованные работы и позволяет повторить
сравнение от сырых данных до таблицы метрик одной командой.

## Зачем это сделано

Статьи и посты о прогнозировании остаточного ресурса обычно сообщают, что
некоторая архитектура показала RMSE такой-то. Повторить результат, как
правило, невозможно: не описан размер окна, не указано, как размечался RUL,
не сказано, считались ли статистики нормализации по обучающей выборке или по
всему датасету, не приведён разброс по сидам.

Здесь каждое из этих решений зафиксировано в коде, одинаково для всех
моделей, и вынесено в README. Цель — не получить рекордное число, а
измерить разницу между подходами в сопоставимых условиях.

## Протокол

Решения, которые сильнее всего влияют на результат, приняты одинаково для
всех моделей:

**Разметка RUL.** Для обучающей выборки RUL считается как разница между
последним циклом юнита и текущим, с ограничением сверху на 125 циклов. Пока
деградация не началась, остаточный ресурс по показаниям датчиков не
восстановим, и модель без ограничения тратит ёмкость на предсказание
неинформативного участка. Значение 125 взято из литературы и зафиксировано.

**Разбиение на обучение и валидацию — по юнитам, а не по окнам.** Соседние
окна одного двигателя почти идентичны. При разбиении по окнам часть
валидации оказывается в обучении, и метрики завышаются. Это самая частая
утечка в работах по C-MAPSS.

**Нормализация — только по обучающей части.** Среднее и дисперсия считаются
на train, затем применяются к валидации и тесту. Статистики теста в
обучение не попадают.

**Отбор признаков.** Семь сенсоров на FD001 имеют нулевую дисперсию и
исключаются: они не несут информации, но искажают нормализацию.

**Тест.** На каждый юнит берётся одно последнее окно — такова постановка
задачи: предсказать остаточный ресурс на момент обрыва записи. Истинные
значения берутся из файла `RUL_FDxxx.txt`.

**Разброс.** Каждая модель обучается на трёх сидах, в таблице приводится
среднее и стандартное отклонение. Разница в полтора пункта RMSE между
архитектурами может целиком объясняться инициализацией, и без разброса это
не видно.

## Метрики

| Метрика | Смысл |
|---|---|
| RMSE | Основная метрика сравнения в литературе по C-MAPSS |
| MAE | Устойчивее к выбросам, показывает типичную ошибку |
| R² | Доля объяснённой дисперсии |
| PHM score | Асимметричная метрика конкурса PHM 2008 |

PHM score стоит в таблице отдельно и заслуживает внимания: он штрафует
запоздалый прогноз сильнее раннего. В эксплуатации пропущенный отказ стоит
дороже лишнего техобслуживания, и RMSE этой разницы не видит. Модель может
выигрывать по RMSE и проигрывать по PHM score — это значит, что она чаще
обещает больше ресурса, чем есть.

## Результаты

Таблица собирается автоматически из файлов прогонов:

```bash
python -m src.report --results-dir results/raw --out results/RESULTS.md
```

Актуальные результаты: [results/RESULTS.md](results/RESULTS.md)

## Что говорят числа

Ниже — прогон на FD001, три сида на модель, среднее ± стандартное
отклонение. Полная таблица в [results/RESULTS.md](results/RESULTS.md).

**Градиентный бустинг — не соломенное чучело.** XGBoost на развёрнутых
окнах оказался первым: 13.79 ± 0.16 RMSE против 13.93 ± 0.48 у GRU и
14.36 ± 0.43 у LSTM. Худший сид XGBoost (13.90) лучше лучшего сида LSTM
(14.01). Что бы рекуррентные модели ни извлекали из временного порядка
внутри окна в 30 циклов, на FD001 это стоит немного.

**Разрыв между XGBoost и GRU — 0.14 RMSE, меньше собственного разброса
GRU по сидам (± 0.48).** Лучший сид GRU (13.26) обходит все три сида
XGBoost. Объявить победителя по одному прогону здесь означало бы выдать
шум за результат.

**Рекуррентность выигрывает у леса, но скромно.** RNN даёт 15.39 ± 0.11
против 16.27 ± 0.22 у Random Forest и выигрывает на каждом сиде. При этом
у простой RNN в четыре раза меньше параметров, чем у LSTM (13 697 против
56 641), а проигрыш по RMSE — 1.03.

**1D-CNN отстаёт заметно:** 18.82 ± 0.65, на пять пунктов хуже XGBoost.
Гиперпараметры брались по умолчанию и отдельно под свёрточную модель не
подбирались — это утверждение о конкретной конфигурации, а не об
архитектуре как таковой.

**RMSE и PHM score расходятся.** У Random Forest RMSE заметно лучше, чем
у 1D-CNN (16.27 против 18.82), но PHM score хуже (659.07 против 648.50):
ошибки леса чаще оказываются на запоздалой стороне, где метрика штрафует
сильнее. XGBoost лучший по обеим метрикам сразу (312.53).

**Разброс по сидам — главная оговорка к таблице.** PHM score у GRU
колеблется от 264.1 до 463.8 на трёх сидах: почти двукратная разница на
метрике, ближе всех стоящей к эксплуатационной цене ошибки.

Короткий вывод: на FD001 выбор между LSTM, GRU и градиентным бустингом
укладывается в шум. Различимы на этих данных только отставание 1D-CNN и
сам разброс по инициализации.

## Запуск

```bash
git clone https://github.com/samishekhalard/rul-benchmark.git
cd rul-benchmark
pip install -r requirements.txt
```

Скачайте датасет C-MAPSS и распакуйте в `data/CMAPSS/` — подробности в
[data/README.md](data/README.md).

Одна модель:

```bash
python -m src.train --model lstm --subset FD001
python -m src.baselines --model xgboost --subset FD001
```

Полный бенчмарк (4 нейросетевые архитектуры, 2 базовые модели, 3 сида):

```bash
bash scripts/run_all.sh FD001
```

На GPU полный прогон занимает около получаса, на CPU — несколько часов.

## Что внутри

```
src/
├── data.py        подготовка данных: разметка RUL, нарезка окон, нормализация
├── models.py      LSTM, GRU, 1D-CNN, RNN
├── baselines.py   XGBoost и Random Forest на развёрнутых окнах
├── metrics.py     RMSE, MAE, R², PHM score
├── train.py       обучение с ранней остановкой и сохранением результатов
└── report.py      сборка таблицы из отдельных прогонов
```

Размеры нейросетей подобраны так, чтобы число обучаемых параметров было
сопоставимым. Иначе сравнение архитектур превращается в сравнение ёмкости.

Базовые модели не умеют работать с последовательностями напрямую, поэтому
окно разворачивается в плоский вектор. Данные и протокол при этом те же —
отличается только способ представления.

## Ограничения

О них честно, поскольку они влияют на то, как читать таблицу:

- **FD001 — самое простое подмножество:** один режим работы, один тип
  отказа. Результаты не переносятся напрямую на FD002 и FD004, где режимов
  шесть. Код поддерживает все четыре подмножества, но выводы в README
  относятся к тому, что прогонялось.
- **Три сида — мало.** Этого хватает, чтобы увидеть порядок разброса, но
  не для статистически значимого утверждения о превосходстве одной
  архитектуры над другой.
- **Гиперпараметры не подбирались отдельно под каждую модель.** Взяты
  разумные значения по умолчанию. Тщательный подбор мог бы изменить
  порядок моделей в таблице.
- **C-MAPSS — симуляция, а не реальные данные с производства.** Шум,
  пропуски и сбои датчиков, с которыми приходится иметь дело в
  эксплуатации, здесь отсутствуют.
