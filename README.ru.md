# Прогнозирование остаточного ресурса оборудования: сравнение архитектур

*[English](README.md) · Русский*

Воспроизводимое сравнение нейросетевых и классических моделей для задачи
прогнозирования остаточного ресурса (Remaining Useful Life, RUL)
промышленного оборудования на датасете NASA C-MAPSS.

Репозиторий сопровождает две опубликованные работы и позволяет повторить
сравнение от сырых данных до таблицы метрик одной командой.

---

## Зачем это сделано

Статьи и посты о прогнозировании остаточного ресурса обычно сообщают, что
некоторая архитектура показала RMSE такой-то. Повторить результат, как
правило, невозможно: не описан размер окна, не указано, как размечался RUL,
не сказано, считались ли статистики нормализации по обучающей выборке или по
всему датасету, не приведён разброс по сидам.

Здесь каждое из этих решений зафиксировано в коде, одинаково для всех
моделей, и вынесено в README. Цель — не получить рекордное число, а
измерить разницу между подходами в сопоставимых условиях.

---

## Протокол

Решения, которые сильнее всего влияют на результат, приняты одинаково для
всех моделей:

**Разметка RUL (обучение).** RUL считается как разница между последним циклом
юнита и текущим, с ограничением сверху на 125 циклов. Пока деградация не
началась, остаточный ресурс по показаниям датчиков не восстановим, и модель
без ограничения тратит ёмкость на предсказание неинформативного участка.
Значение 125 взято из литературы и зафиксировано.

**Истинные значения теста: без ограничения.** Метки RUL из файла
`RUL_FDxxx.txt` используются как есть, без ограничения сверху. Ряд
реализаций применяет ограничение на 125 и к тестовым меткам — этот
репозиторий так не делает. Соглашение явно указано, чтобы результаты можно
было сопоставлять с кодом, использующим противоположный подход.

**Разбиение на обучение и валидацию — по юнитам, а не по окнам.** Соседние
окна одного двигателя почти идентичны. При разбиении по окнам часть
валидации оказывается в обучении, и метрики завышаются. Это самая частая
утечка в работах по C-MAPSS. Количественное измерение эффекта — в разделе
[«Эксперимент с утечкой»](#эксперимент-с-утечкой).

**Нормализация — только по обучающей части.** Среднее и дисперсия считаются
на train, затем применяются к валидации и тесту. Статистики теста в
обучение не попадают.

**Отбор признаков.** Семь сенсоров на FD001 имеют нулевую дисперсию и
исключаются: они не несут информации, но искажают нормализацию.

**Тест.** На каждый юнит берётся одно последнее окно — такова постановка
задачи: предсказать остаточный ресурс на момент обрыва записи.

**Разброс.** Каждая модель обучается на трёх сидах (42, 1337, 2024); в
таблице приводится среднее и стандартное отклонение. Разница в полтора
пункта RMSE между архитектурами может целиком объясняться инициализацией,
и без разброса это не видно.

## Метрики

| Метрика | Смысл |
|---------|-------|
| RMSE | Основная метрика сравнения в литературе по C-MAPSS |
| MAE | Устойчивее к выбросам, показывает типичную ошибку |
| R² | Доля объяснённой дисперсии |
| PHM score | Асимметричная метрика конкурса PHM 2008 |

PHM score стоит в таблице отдельно и заслуживает внимания: он штрафует
запоздалый прогноз сильнее раннего. В эксплуатации пропущенный отказ стоит
дороже лишнего техобслуживания, и RMSE этой разницы не видит. Модель может
выигрывать по RMSE и проигрывать по PHM score — это значит, что она чаще
обещает больше ресурса, чем есть.

```
d = y_pred − y_true

d < 0  (ранний прогноз): exp(−d / 13) − 1
d ≥ 0  (запоздалый):     exp( d / 10) − 1
```

При |d| = 10: ранний штраф ≈ 1.16; запоздалый ≈ 1.72.

## Эксперимент с утечкой

Во многих работах по C-MAPSS train и validation делят перемешиванием
скользящих окон. Соседние окна одного двигателя почти идентичны, поэтому
модель валидируется на том, что фактически уже видела. Этот репозиторий
измеряет эффект, а не утверждает его.

LSTM, FD001, три сида, одинаковые гиперпараметры, различается только
разбиение:

| Разбиение | Val RMSE     | Test RMSE    | Разрыв val–test |
|-----------|--------------|--------------|-----------------|
| по юнитам | 13.53 ± 0.22 | 16.49 ± 0.41 | +2.97           |
| по окнам  | 3.25 ± 0.19  | 19.01 ± 0.67 | +15.77          |

Воспроизводится командой `bash scripts/leakage_experiment.sh`.

**Val RMSE 3.25 выглядит как рекорд.** Опубликованные результаты на FD001
держатся в районе 11–13. Статья с цифрой 3.25 сообщает не о лучшей модели,
а о собственном разбиении данных.

**Утечка не только приукрашивает отчёт — она ухудшает модель.** Тестовая
метрика честная при обоих разбиениях, и она падает: 16.49 → 19.01, то есть
на 15%. Механизм — ранняя остановка. Она смотрит на валидацию, а при утечке
валидация продолжает улучшаться, пока модель запоминает почти одинаковые
окна, и обучение не останавливается вовремя. Время прогона подтверждает:
24–37 секунд при честном разбиении против 105 секунд при утечке — то же
значение patience, втрое больше эпох.

Уточнение: в режиме window статистики нормализации тоже считаются по всем
обучающим строкам, включая те, из которых собраны валидационные окна. Оба
эффекта входят в воспроизводимую методологию, и измеренный разрыв отражает
их совокупность.

## Что говорят числа

Ниже — прогон на FD001, три сида на модель, среднее ± стандартное
отклонение. Полная таблица в [results/RESULTS.md](results/RESULTS.md).

**GRU впереди, XGBoost следом — но разрыв в пределах шума.** GRU занимает
первое место с RMSE 15.09 ± 0.14; XGBoost — второе с 15.23 ± 0.23. Разрыв
0.14 равен собственному разбросу GRU по сидам. На лучшем сиде обе модели
пришли к 14.93 и 14.92 — разница 0.01. Объявить победителя по трём
запускам означало бы принять инициализацию за архитектурное преимущество.

**XGBoost выигрывает по PHM score, проигрывая по RMSE.** RMSE ставит GRU
выше; PHM score меняет порядок: 347.35 (XGBoost) против 434.48 (GRU).
Ошибки XGBoost тяготеют к раннему прогнозу; ошибки GRU — к запоздалому,
который метрика штрафует сильнее. Таблица с одним только RMSE это скрывает.

**Простая RNN воспроизводит LSTM с меньшим числом параметров.** Разрыв по
RMSE — 0.04 (16.31 ± 0.76 против 16.26 ± 0.55), не различимый внутри
разброса. RNN выигрывает у LSTM по PHM score (553.79 против 607.30) и
делает это при 32,993 параметрах против 57,153 у LSTM — в 1.7 раза меньше.
Рекуррентность также выигрывает у леса на каждом сиде: худший прогон RNN
(17.29) лучше лучшего прогона Random Forest (17.57).

**CNN — последняя и наименее стабильная модель.** 20.19 ± 1.26 — почти
пять пунктов RMSE позади XGBoost. По PHM нестабильность ещё заметнее:
±431.19 против ±143.15 у следующей по нестабильности модели. PHM score у
CNN колебался от 687 до 1699 на трёх сидах — разница в 2.5 раза на
метрике, ближайшей к эксплуатационной цене ошибки. Гиперпараметры для
свёрточной архитектуры отдельно не подбирались: это утверждение о
конкретной конфигурации, а не об архитектуре в целом.

**Короткий вывод:** на FD001 выбор между GRU, XGBoost, LSTM и RNN
укладывается в шум инициализации. Различимы только отставание CNN и сам
масштаб разброса по сидам.

## Запуск

### 1. Установить зависимости

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### 2. Скачать данные

Скачать `CMAPSSData.zip` из NASA Prognostics Data Repository и распаковать
`.txt`-файлы в `data/`. Подробности — в [`data/README.md`](data/README.md).

### 3. Запустить полный бенчмарк (все модели, 3 сида)

```bash
bash scripts/run_all.sh data/ 100
```

### 4. Обучить одну модель

```bash
# Нейронная сеть
python src/train.py --model lstm --subset FD001 --data-dir data/ --epochs 100

# Бейзлайн
python src/train.py --model xgboost --subset FD001 --data-dir data/
```

### 5. Сгенерировать таблицу результатов

```bash
python src/report.py --results-dir results/raw --output results/RESULTS.md
```

### 6. Запустить тесты

```bash
pytest tests/ -v
```

### 7. Линтер

```bash
ruff check src/ tests/
```

## Ограничения

- **FD001 — самое простое подмножество:** один режим работы, один тип
  отказа. Результаты не переносятся напрямую на FD002 и FD004, где режимов
  шесть. Код поддерживает все четыре подмножества, но выводы в README
  относятся к тому, что прогонялось.
- **Три сида — мало.** Этого хватает, чтобы увидеть порядок разброса, но
  не для статистически значимого утверждения о превосходстве одной
  архитектуры над другой.
- **Гиперпараметры не подбирались отдельно под каждую модель.** Взяты
  разумные значения по умолчанию. Тщательный подбор мог бы изменить
  порядок моделей в таблице.
- **C-MAPSS — симуляция, а не реальные данные с производства.** Шум,
  пропуски и сбои датчиков, с которыми приходится иметь дело в
  эксплуатации, здесь отсутствуют.
